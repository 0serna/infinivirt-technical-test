# Soft-delete for User and Client catalogs

Administrator catalog management uses soft-delete (`deletedAt`) with restore, not hard-delete and not an `active` boolean. Hard-delete fights `onDelete: Restrict` on Ticket and history FKs; omitting delete leaves no way to deactivate staff or retire a Client from pickers. Soft-deleted rows stay out of operational catalogs (Ticket create Clients, Assignee Users) and cannot authenticate (Users); existing Ticket projections still show their name/displayName. Uniqueness of User email and Client name remains global (including soft-deleted rows): create conflicts with a tombstone at 409; restore cannot collide because the soft-deleted row still holds the key. Soft-deleted rows are not edited until restored. Soft-delete does not auto-unassign Tickets. Because User email is immutable, a soft-deleted email stays reserved for that User (reactivate via restore) and cannot be handed to a different User without hard-delete, which is out of scope.
